## Owner inputs, risks and decision boundary

- The owner must supply legally approved `minimumDays`/authority/lawful basis and automatic archive criterion, **not** a developer-provided default; no ID capture until both policy and feature flag are approved. `secureDeleteAfterDays` records a threshold but authorizes **no** delete/purge job. Previously archived DRAFT records can reopen but remain undeletable; previously issued SENT/RECEIVED remain immutable under existing rules.
- Only the DBA/operator may identify/provision the existing approved migration login, runtime role, privileged cluster-role backup reader, restricted remote storage, separate isolated restore host/DB, key custody, mounted asset directory, alert mailbox, backup calendar/retention and documented RPO/RTO. `pg_dumpall --roles-only` includes **cluster-wide role metadata** and needs explicit DBA scope approval; stop on a shared cluster if that exposure is not authorized. Offsite share writable by the approved UID is not inherently immutable; separate immutable snapshots/object lock need infrastructure review. The signed counts and private asset inventory are compared before and after dumping; an active write workload may repeatedly fail this deliberately conservative check, so owner must approve a quiet window compatible with RPO or review a snapshot-based backup design. Storage/fsync and ownership incompatibilities fail closed, not bypassed.
- Postflight proves public-schema object privileges, signed row counts, trigger counts and role capability probes; the isolated script does **not** change database ownership or database-level grants, so DBA must independently compare **database-level ACLs and effective runtime connections** on the isolated recovery target as well as the owner DB before declaring access-control preservation. Original attachment rows generally have no individual content digest; the signed encrypted archive and asset-presence checks do not prove a separately recorded per-attachment source hash. Historical artwork hashes are checked against the DB. Full RTO includes provisioning/app start, not only the restore command. A cold script/content test cannot substitute for an executed recovery exercise.
- The current sandbox cannot satisfy the roadmap's **live archive/retention + executed off-server restore** exit conditions. Follow the ordered runbook; record every mandatory PASS/FAIL, fix issues in a new reviewed change if necessary, and announce deployment only after all stages pass. No Phase 13 work is included or authorized.
