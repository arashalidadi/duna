# Phase 8 — document templates and output (2026-10-15)

This implements the **revised**, decision-backed Phase 8 in `docs/source-material/project-audit.md` (§P8), not the old Customer 360 plan. The specification in `duna-analysis` is unchanged.

## Delivered

- **11 types:** Loading List, B/L, Manifest, Invoice, Delivery Order, Release Order, Salary Slip, Voucher, Payment, Receipt, and Ledger. Each associated office screen has authenticated PDF, Excel and Print actions. Payment and Receipt are type-checked views of Voucher rows; Ledger uses the existing customer-statement calculation and its selected date/currency filters. A manifest includes B/L and party references, units/packages/weight and a final totals row.
- **Template management:** permission-controlled declarative JSON layouts (not uploaded executable HTML or arbitrary storage paths); immutable, SHA-256-checked stored versions; audited assignment/deactivation history; record preview; protected PNG/JPEG company logo, letterhead, stamp and signature upload/approval/retirement. The UI can import a layout JSON file and upload artwork. Legacy registry read-path aliases and its paginated list envelope remain; the old client-supplied `storageKey` write is intentionally rejected in favor of validated server-managed content.
- **Output:** server-side DejaVu PDF with an all-pages DRAFT watermark for editable documents, a LIVE watermark for the ledger, and approved assigned stamp/signature artwork in **issued PDF only** (never a draft). Print generates a separate PDF without either approval mark (but may retain the ordinary company logo/letterhead). Excel contains exact money strings and escapes formula-leading input. Source projections use explicit allow-lists; Excel and PDF use the same projection. File downloads go through the existing authenticated same-origin proxy with no token in the URL.
- **New issuance-time preservation:** in the transaction that finalizes/approves/posts a new operational record, `DocumentIssuedSnapshot` captures the document projection, company identity and assigned template version (or the then-current generic fallback layout when no version is assigned). Covered transitions are load-list finalization, B/L approval (both issue paths), manifest approval, invoice issuance, DO/RO creation, salary approval, and voucher posting (both generic and payment/receipt outputs). A failed capture rolls back that issuance. Issued PDF/Print/Excel are produced on request from this frozen snapshot, and first generated bytes are then SHA-256-checked and archived, one row per format. Subsequent changes to company identity, related parties, live record fields, or template assignment cannot change these snapshots or previously archived bytes. The live ledger and drafts are *not* issuance snapshots or archives. Output/history/archive APIs enforce both `document:render` and the source read permission; preview also requires `document:manage`. Portal-linked principals are denied office output even if such grants are accidentally assigned. Assignment/artwork approval requires both `document:manage` and `document:approve`, except for the primary administrator's existing implicit authority.

## Existing documents and accuracy limits

Older issued records **do not have issuance-time snapshots**. They are not backfilled with invented original values: their first requested output is explicitly labelled **“Legacy record: reconstructed on first render; original issuance-time appearance cannot be verified.”** Its bytes are then archived against a stable issuance key. Previously stored TRN on an invoice is used rather than today's setting. Existing records whose original issuance timestamp is missing cannot be retroactively authenticated. No operational rows are rewritten.

The official company's template files were not provided (DEC-098/REQ-125). The built-in layout and its English field captions are **generic, not company-approved forms**; their visual/legal fidelity cannot be signed off until official templates are collected and compared. Approved marks appear only when an authorized operator has assigned actual approved artwork. Identity-document attachments and recipient/employee sign-off workflows are not replaced by company-artwork uploads.

## Migration and operational review

`prisma/migrations/20261015010000_phase8_document_output/migration.sql` is additive: a nullable `DocumentTemplateVersion.contentHash` and four new tables (`DocumentTemplateAssignment`, `DocumentAsset`, `DocumentIssuedSnapshot`, `DocumentRenderedOutput`). It neither updates nor deletes existing document rows. Its prefix sorts before the already-existing, independently additive Phase-7 migration named `20261016000000`; this is a filename chronology inherited from earlier work, **not** a request to rewrite applied migration history. Inspect the *target* database's migration status and schema before applying anything. No database migration, seed, schema push, reset, or E2E run on an owner database was performed in the agent workspace. Do not seed demo data unless explicitly requested; `seedCore` only adds the three permission codes idempotently and grants them to ADMIN through the existing role-permission mechanism.

The rendered archive stores bytes inside PostgreSQL. Layout JSON and artwork live in the existing private storage adapter; retain those immutable files to allow first downloads of issued snapshots that have not yet been rendered. The source snapshot cannot reconstruct missing artwork bytes. Retiring an asset after issuance does not block retrieval for the actual snapshot-capture time (even when a display date was backdated) while the storage object still exists and passes its hash check.

## Local verification

The DB-free Phase-8 unit script exercises all eleven projections and all three renderer modes for all eleven types, checks PDF-versus-Print mark access, a multi-page draft watermark, manifest totals, spreadsheet formula escaping/exact decimal strings, layout validation, permissions, issuance-time capture versus later company/party/template changes, and immutable archive read-back. A separate DB-free Jest HTTP suite checks binary responses and authorization gates. API/web typechecks, the existing web static/contract/translation checks, and Prisma schema validation/client generation were run locally. Prisma validation/generation used only a nonconnecting local URL and engine overrides because engine downloads and an owner PostgreSQL connection are unavailable here; they **do not verify migration application**. The owner previously reported portal-isolation **3/3** and pre-Phase-8 full E2E **29/29 suites, 548/548 tests** on the server; those are not Phase-8 results and were not repeated here.
