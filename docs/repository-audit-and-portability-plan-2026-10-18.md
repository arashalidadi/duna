# Duna ERP — repository audit and portability plan

**Audit date:** 2026-10-18. **Status:** proposed findings and work packages for owner review; **not** an implementation plan approved for execution. This is one new, additive audit report. No pre-existing documentation, source, database, service, schedule, or deployment was changed for this audit. The repository examined here is `/home/user/duna`, **not** the owner's `/home/duna/shipping-dashboard/new-erp`; the owner host was not accessed.

**Evidence language:** **Source-confirmed** means a behavior or mismatch follows from inspected code/docs, not that it has been reproduced on a live server. **Reported verified** identifies the owner's recent test/browser evidence or a dated prior test result with its environment. **Unverified** is not the same as failed or missing. Old phase numbers inside September migration names and `docs/progress.md` are *not* the revised implementation roadmap's phase numbers.

## A. Executive summary

The working tree contains a substantial, functioning shipping ERP: a pnpm monorepo with Next.js/React, NestJS, PostgreSQL/Prisma, 40 API feature directories, 44 dashboard pages, shared contracts, 94 Prisma models, 44 enums, and 48 ordered migration directories. The current revised roadmap ends at **P12 (13 phases, P0–P12)**; it defines no P13. Phase 10 is recorded as owner-accepted, Phase 11 is owner-approved, and the owner now reports **`PHASE12_TEST_PASS: 27 stages passed; owner DB queries read-only; no migration, seed, timer or production fixture writes`**, plus successful manual review of relevant dashboard workflows and Retention & Automatic Archive Policies/category values. These are current positive findings, not a claim that the test command executed a backup, restore, or migration.

**Strengths:** default-deny Nest authorization with a separately constrained primary administrator; portal scoping; transactionally audited accounting/corrections and immutable posted journals; production-safe versus explicitly opt-in demonstration seeding; a guarded Phase 12 owner-host workflow; and implemented encrypted/signed backup and isolated-restore *tools*. Browser checks and unit/E2E coverage also exist, but their scopes differ.

**Priorities established by this audit:**

1. **Safe new-install bootstrap:** `prisma/seed/core.ts:425-456` has a hardcoded fallback for `SEED_ADMIN_PASSWORD` while the root `.env.example` does not request one. On an empty database, core seed can create the uniquely authoritative primary administrator with a predictable bootstrap credential if the operator omits the variable. This is a source-confirmed *new-install risk*; no claim is made about the owner's existing password. A fail-closed, pre-write bootstrap contract is needed before presenting the existing quick start as a production installer.
2. **Security closeout and redaction:** incident `docs/source-material/project-audit.md` is last documented **OPEN**; provider-side rotation/closure is not established here. Separately, `apps/api/src/common/filters/http-exception.filter.ts:49-66` uses the full request URL in error paths and 500 logs, while attachment downloads use a signed credential in a query parameter (`attachment.service.ts:198-231`, `attachment.controller.ts:74-78`). Redacting sensitive URL parameters before logging or returning error paths is a concrete, narrow security correction. No secret values were examined or copied into this report.
3. **Operator/documentation truth:** `README.md:5` still announces an older “Phase 6”; its start/stop instructions claim they control PostgreSQL, but `scripts/start-dev.sh`, `stop-dev.sh`, and `phase11-apps.mjs` explicitly manage **API/Web only**. `docs/operations.md` and a warning in `docs/phase10-deployment.md` repeat the old assumption. The README's generic `prisma migrate dev` quick start is not the guarded owner-server upgrade procedure and cannot use the restricted runtime role. Existing `.env.example` files omit several separately required asset, notification, backup and bootstrap settings. These discrepancies matter to a new operator.
4. **Release baseline and disaster-recovery evidence:** this audit's local Git `HEAD` and worktree do not presently match a clean remote-tip checkout (details in H). This is a release-provenance **verification issue**, not evidence of a faulty deployment. The P12 roadmap's scheduled off-server backup and successfully executed/documented restore are **Unverified** by the 27-stage read-only test. Code exists for the recovery operations; do not confuse availability with owner activation or a signed restore receipt.

No current broken dashboard button or failed Phase 12 owner test was established. A narrower retention-only permission/UI inconsistency is described in D/E; it was not reported as a live browser failure. Historical Phase 12 catalog/Save problems in dated reports must not override the owner's newer PASS and browser observations.

## F. Clean-install and portability plan (proposed; **not run**)

**Separate three procedures:** (1) disposable developer install with its own DB; (2) new-server **empty-database production-style installation**; (3) upgrade/move of an existing populated installation. Neither the dev Compose/standalone helpers (default `shipping_erp`) nor Phase 11/12 owner-specific `duna_seed_test`/`erp-postgres` hard stops are a generic new-server provisioning command. Keep those protections intact; devise a separately reviewed new-host path rather than changing a target name in place.

**A new operator's intended sequence after approval:**

1. **Acquire a reproducible release artifact.** Resolve the local-versus-remote Git baseline without discarding work; use an exact reviewed commit and lockfile, confirm source/digest and prerequisites. Support documented Node version(s), a known pnpm 9 release (owner reports 9.15.9 and no Corepack), PG16 server/client, native Prisma engine compatibility, and required PDF/font/runtime libraries. Avoid a hidden Corepack assumption. Identify whether Docker is only for development or an approved production service manager exists.
2. **Inventory persistence and roles before provisioning.** For a *new* host only, have the DBA create/review an empty PG16 DB/schema and distinct privileged migration owner and least-privilege API runtime identities; verify actual connection destination and journal ownership. Do **not** repoint the existing owner's restricted `DATABASE_URL`, use `duna_seed_test1`, start a second DB on the owner, or reuse a P12 hard-coded workflow as a generic installer. For a transfer, plan the approved data-and-assets restore, not a new blank seed over old records.
3. **Supply private configuration, never example secrets.** Provide root API `NODE_ENV`, `APP_TIMEZONE`, `APP_DEFAULT_CURRENCY`, API bind/port/version/CORS, runtime `DATABASE_URL` and unique JWT secrets; Web `NEXT_PUBLIC_API_URL` (same-origin `/api/v1`) and server-only `API_INTERNAL_URL`; a protected, explicit one-time `SEED_ADMIN_*` bootstrap; an absolute private `ATTACHMENT_STORAGE_DIR`; optionally SMTP/worker settings; separately protected migration, backup/restore, signing, encryption, alert and storage settings. Describe env precedence and file permissions. An owner URL must never replace the runtime URL or enter child Web/tests/logs. No secret values belong in Git or this guide.
4. **Install/build/replay in a separately approved empty target.** Install exactly locked dependencies, generate the *real* Prisma client, build config/shared/API/Web and check the canonical API artifact. Read-only inspect target/journal/history first; only then use a **reviewed migrator identity** to apply the 48 committed migrations. On new installs verify the P10 data-preserving column transition, P11 role/ACL and P12 constraints/triggers. Bootstrap **only** approved reference data/primary admin with a unique operator-supplied secret, confirming its role/grants; never run demo scripts by default. Use isolated fixture DBs for mutation/E2E acceptance. This is a plan, **not permission** to run `db:migrate`, `db:migrate:reset`, `db:seed` or `phase12:apply` against any current server.
5. **Install persistence and process/network boundaries.** Provision external private attachment filesystem and backup of its bytes alongside the DB; note that a repository copy omits them. Configure the approved API/Web manager (API 3101, Web 3000 are defaults), a TLS reverse proxy mapping same-origin `/api/v1`, explicit API CORS origins, bounded uploads, logs with URL-credential redaction, health monitoring, and optional verified SMTP. The browser must not target a server's loopback address; the Next proxy does that server-side. Protect off-server encrypted backup storage, keys and role dumps separately; arrange a monitoring/restore schedule only after owner approval.
